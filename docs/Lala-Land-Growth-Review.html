SEO, AEO and GEO findings

The biggest eligibility issue is the existing pre-launch noindex/disallow configuration. Keep it deliberate until the approved public host, business information and operational booking checks are ready. Then change both controls together and verify the rendered page, robots, sitemap, canonical and Search Console inspection. Publishing more content while crawl access is blocked will not resolve discovery.

For answer and generative search, the useful improvements are explicit business identity, direct practical answers, meaningful service information and credible first-hand evidence. Google’s current guidance ties generative search to foundational SEO; it does not require special AI files or markup. FAQs were added for customers, without promising FAQ rich results; Google’s documentation states those results are no longer shown.

The partial locality schema is truthful, but it is not a completed Google LocalBusiness eligibility implementation. Never fill missing street address, ratings, prices, hours or credentials simply to pass a validator. A region in the catchment is not a physical branch.

CRO and the booking journey

The intended journey is local discovery → service/price/proof evaluation → request → Bianca’s follow-up → confirmed visit → completed appointment → optional review/rebooking. The website now communicates requests clearly, but the middle of the decision still lacks a real menu and first-hand proof. Two earlier simulated client reviewers independently identified these gaps; this is qualitative agent feedback, not behavioural analytics or actual customer research.

Operational finding: the inspected booking API stores requests in D1 and the admin interface. No email notification step was present in that route. Before promotion, test one approved disposable request end to end, establish who checks the admin queue, confirm the follow-up process and publish a reliable fallback contact. Do not assume a form success message means Bianca has been alerted. No real test booking was created in this review.

Protection finding: contact-based duplicate suppression and a honeypot are present; they are not a robust general rate limit. Review request throttling, privacy/retention, date validation and admin access as a separate pre-campaign technical task. This was not an exhaustive security audit.

Measurement and decision rules

No analytics, Search Console, Google Business Profile insights, heatmaps or CRM performance were inspected. Traffic, conversion, current rankings and AI visibility are unknown. The configured analytics domain is null, so source event calls are not evidence of a working reporting pipeline.

Track discovery source → request received → contacted → confirmed → completed → rebooked, using non-sensitive events and approved privacy handling. Define a qualified inquiry as a reachable person seeking a supported service at the Scarborough location. Report confirmed appointments / qualified inquiries, show-ups / confirmations, and rebookings / completed clients. Separate spam, duplicates, internal tests and cancellations. Use America/Toronto reporting dates. The first live month establishes a baseline; do not claim uplift without a valid comparison.
